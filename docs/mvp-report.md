# PhishingEml MVP 阶段报告

> 报告日期：2026-09-07  
> 对照范围：原始设计文档、详细实现方案、阶段 A 共享契约、当前源码、自动化测试和真实联调记录。  
> 当前定位：面向课程展示的钓鱼邮件静态分析与检测 Web 原型，不是生产级邮件安全网关。

## 1. 报告结论

当前版本已经完成了 MVP 的核心闭环：

```text
上传/粘贴/选择本地样本
  -> MIME、正文、URL、附件静态解析
  -> 固定规则检测 + TF-IDF/Logistic Regression 推理
  -> 规则分与模型概率融合
  -> 风险等级、证据和处置建议
  -> SQLite 保存检测历史
  -> 前端展示结果、历史、黑名单、统计和知识库
```

与原始设计相比，项目当前不是“功能未完成的骨架”，而是一个可演示的单封邮件分析平台。核心差异主要有三类：

1. **核心能力已实现，但部分范围收窄**：模型当前使用主题和纯文本，不包含原设计建议的结构化特征融合；解析器提取邮件头，但不做 SPF/DKIM/DMARC 验证。
2. **增强能力只实现了展示级或最小闭环**：黑名单支持本地手工维护和匹配，但尚未完成 CSV 导入；反馈只校验并写日志，不持久化、不触发重训。
3. **课程原型边界保持得较好**：不访问邮件 URL、不解压或执行附件、前端通过文本节点安全展示邮件内容、上传大小和输入来源均有校验。

综合判断：**MVP 已达到课程展示和基本版验收要求；下一阶段应优先补齐可复现性、指标解释、结构化特征、反馈持久化和安全回归测试，而不是继续堆叠页面。**

## 4. 分模块分析

### 4.1 输入、样本与 API 契约

**原始设计。** 设计要求三种输入严格互斥，上传文件限制 5 MB，原文限制 200000 字符，样本只能来自受控目录，并统一返回成功/错误结构。

**当前实现。** `POST /api/emails/analyze` 已落实 `file`、`raw_text`、`sample_id` 严格三选一；`INPUT_REQUIRED`、`INPUT_CONFLICT`、`EMPTY_INPUT`、`INVALID_FILE_TYPE`、`FILE_TOO_LARGE` 等错误码已进入共享契约。前端同时提供文件、文本和本地样本入口。

**差异与评价。** 这是当前最完整的模块之一。原始设计中的“首次使用者 1 分钟内完成检测”也具备实现基础。尚未实现的主要是批量上传、结果导出和用户身份上下文；这些不影响单封 MVP，但会影响后续运营和实验统计。

**下一步。** 增加请求级审计信息、统一的输入来源统计，并补充超大文本、异常编码和路径穿越的 API 回归用例。

### 4.2 MIME、正文与附件解析

**原始设计。** 计划提取 From、To、Cc、Reply-To、Return-Path、Subject、Date、Message-ID、Received 链路、纯文本、HTML、超链接、附件元数据，并在存在时读取 SPF/DKIM/DMARC 相关头；损坏 MIME 尽量恢复并记录警告。

**当前实现。** `email` 标准库解析普通和 multipart 邮件；使用 `raw_items()` 规避异常 `Message-ID` 触发 500；提取主题、地址、日期、Message-ID、正文、HTML、URL、附件大小/哈希/扩展名/MIME/risk hints，并保留 `parse_warnings`。附件只读元数据，不解压、不执行。

**差异与评价。** 基本解析闭环已达标，且真实联调暴露的问题已经修复。与原始设计相比，当前还没有专门的 Received 路径解析、认证头结构化字段，也没有把“认证头存在”与“认证通过”进一步区分的展示层。该差异属于分析深度不足，不是安全边界缺失。

**下一步。** 先增加结构化 `auth_results`/`received_hops`（只读原文，不进行认证验证），再为每个字段增加缺失/异常测试；不要在 MVP 后续版本中引入在线认证或外部 DNS 查询。

### 4.3 URL 静态分析与黑名单

**原始设计。** 设计覆盖协议、主机、注册域名、IP、短链接、长路径、特殊字符、紧迫词、发件人域名关系和离线黑名单。

**当前实现。** `url_parser.py` 已完成 URL 提取、HTML `<a>` 解析、规范化、IDN 转换、注册域名、IP、非 HTTPS、短链接、长 URL、userinfo、编码字符、多级子域、Punycode 和可疑 token；黑名单在分析时使用精确 URL 或注册域名匹配，并将命中信息写入结果。

**差异与评价。** 静态分析目标基本兑现，但当前 URL 特征仍主要用于规则解释，尚未进入模型的结构化特征向量；黑名单管理也更接近本地控制台，而不是可持续更新的情报管道。原方案提出的 PhishTank/CSV 离线导入脚本目前不存在。

**下一步。** 优先实现受控 CSV 导入、规范化去重和导入报告；随后再评估把 URL 数量、协议、域名关系等特征加入模型，而不是直接增加更多关键词。

### 4.4 规则检测与风险评分

**原始设计。** 规则 R01-R10，规则分设置上限，避免重复计分，并输出规则编号、描述、贡献分数和证据；风险区间为低 0--29、中 30--59、高 60--100。

**当前实现。** `RULE_CATALOG` 定义 R01-R10，规则函数独立执行，按规则编号去重后总分截断为 100；`fuse_scores()` 固定使用模型 65% + 规则 35%，风险阈值为 30/60；`DetectionResult` 会校验融合分数、风险等级和模型标签的一致性。

**差异与评价。** 评分语义已冻结且实现稳定，解释链路清晰。差异在于规则分值和词典仍写在代码中，教师或演示人员不能通过配置文件调整；规则贡献目前是“每条规则一次”，没有按多 URL、多附件提供细粒度贡献。

**下一步。** 把规则目录、词典、阈值和版本号迁移到受校验的配置文件；保留当前默认值，新增离线回放脚本评估阈值变化对误报/漏报的影响。

### 4.5 机器学习、模型版本与实验

**原始设计。** 先做 TF-IDF 基线，再比较朴素贝叶斯、逻辑回归、线性 SVM；训练前去重、清洗、划分，避免数据泄漏；模型应保存版本、随机种子、特征配置、指标和错误样本。

**当前实现。** 当前模型为版本化的 TF-IDF + Logistic Regression Pipeline，特征版本 `text-v1`，模型文件有 SHA-256 完整性校验；训练/验证/测试数量、标签顺序、阈值诊断、混淆矩阵和数据集版本写入 `model_meta.json`。文本清洗对邮箱、URL、长数字做占位符替换并限制 20000 字符。

**差异与评价。** 可复现基线已经形成，但当前推理只使用 `subject + text_body`；原始方案建议的 URL、附件、地址关系等结构化特征，以及多模型对比页面尚未实现。更需要注意的是：模型元数据的离线测试指标（F1 0.9844）与 980 封真实上传联调指标（F1 0.9703）口径不同，当前页面容易让观众误以为它们是同一批数据的结果。

**下一步。** 在模型指标页面明确区分“训练测试集”“跨来源评估”“端到端联调”三类指标；补充固定外部评估集和按来源的误报/漏报案例，再决定是否引入结构化特征或第二个模型。

### 4.6 结果解释、历史和持久化

**原始设计。** 结果必须能回答“为什么可疑”，并保存检测编号、哈希、文件名、时间、风险、模型版本、规则数量、URL/附件数量和反馈；历史支持列表、详情、筛选和删除。

**当前实现。** 结果返回模型概率、规则分、最终分、风险等级、模型版本、解释证据、URL、附件、建议和解析警告；SQLite 保存邮件、URL、附件、检测和黑名单关联；历史 API 提供分页、风险筛选、详情和删除；前端用 `textContent`/文本节点展示邮件字段，未把原始 HTML 直接插入页面。

**差异与评价。** MVP 目标已满足。当前反馈没有数据库表，`POST /api/feedback` 只做校验和日志；历史没有 CSV/JSON 导出，也没有按来源、时间范围和模型版本筛选。数据库契约要求的级联删除和参数化查询已在 Repository 层落实，但还应增加更明确的安全回归测试。

**下一步。** 先持久化反馈并建立反馈与检测的关联，再实现历史导出和按模型版本筛选；导出必须默认去除正文、地址等敏感原文。

### 4.7 黑名单、统计看板和知识库

**原始设计。** 黑名单是增强功能；统计看板应展示风险分布、趋势、规则排行、模型指标和混淆矩阵；知识库提供防范知识与典型案例。

**当前实现。** 黑名单支持新增、查询、关键词/状态筛选、停用和命中次数；看板有风险饼图、按 UTC 日期趋势、规则排行、模型指标卡；知识库已内置 27 篇文章、6 个专题，支持分类、搜索、详情、关键要点、步骤和案例对比。

**差异与评价。** 黑名单、统计、知识库的展示闭环已超过基本版要求。当前统计更偏运营展示，尚未支持时间范围筛选、模型对比、混淆矩阵可视化、误报/漏报钻取；黑名单没有真正的离线 CSV 导入入口；知识库是代码内置数据，不是可编辑内容源。

**下一步。** 以“可验证性”优先：增加看板口径说明、模型评估数据集标签、混淆矩阵和错误样本入口；再考虑将黑名单与知识库迁移到可版本化的 JSON/SQLite 数据源。

### 4.8 前端、安全边界与部署

**原始设计。** 原生 HTML/CSS/JavaScript + ECharts；页面要有 loading、空状态、错误状态；邮件 HTML 必须转义，URL 不能成为真实外链；本地 127.0.0.1 演示。

**当前实现。** 单页多视图前端覆盖欢迎页、检测、历史、黑名单、看板和知识库；使用本地 ECharts；加载、空数据、错误、模型未就绪等状态均有处理；邮件正文和 URL 以文本节点展示，未设置可点击 URL；`ALLOW_NETWORK=true` 会拒绝启动，明确保持静态分析边界。

**差异与评价。** 当前实现与课程演示定位一致。原始方案中的账号/权限和生产部署本来就是可选或不建议范围，因此不应把它们视为 MVP 缺陷。需要继续关注的是浏览器端安全回归、长正文布局、移动端可读性和异常响应的用户提示一致性。

## 6. 下一步优化路线

### P0：先解决可信度和安全回归

1. **统一指标口径。** API 和看板同时标注数据集名称、样本数量、评估阶段和阈值；明确离线测试指标与端到端联调指标不能直接比较。
2. **补齐反馈持久化。** 新增 feedback 表和查询接口，记录检测编号、标签、备注、时间；暂不自动重训，先形成可审计数据。
3. **扩展安全测试。** 增加 XSS 字符串、恶意 HTML、超大 multipart、异常 MIME、路径穿越、重复黑名单和删除级联测试。
4. **固定演示数据和启动检查。** 从空数据库启动，验证模型哈希、样本目录、数据库初始化和 `ALLOW_NETWORK` 拒绝逻辑。

### P1：补齐原设计中最有价值的能力

1. **结构化邮件特征。** 在保持 `text-v1` 兼容的前提下新增特征版本，加入 URL 数量、附件数量、From/Reply-To 域名关系、HTTPS/IP/短链等特征，并用固定验证集比较收益。
2. **黑名单离线导入。** 支持 CSV/JSON 导入、规范化去重、来源和置信度校验、导入摘要及失败行报告。
3. **模型与错误分析页面。** 展示混淆矩阵、按数据源指标、典型误报/漏报，并链接到静态证据而不暴露敏感原文。
4. **解析字段增强。** 增加 Received 跳数、认证相关头的只读结构化展示，并为缺失/异常字段提供统一解释。
5. **历史导出与筛选。** 增加时间、来源、模型版本筛选和脱敏 JSON/CSV 导出。

### P2：在基本版稳定后再考虑

1. 多模型对比和可配置阈值实验。
2. 批量检测和异步任务。
3. 知识库从代码常量迁移为可版本化内容源。
4. 账号、角色和部署脚本。若引入这些功能，必须重新评估隐私、权限和运维范围，不能改变静态分析安全边界。

## 7. MVP 结论

当前版本可以作为 `v0.2-mvp` 级别的课程演示版本：核心流程闭环、接口契约清晰、规则和模型有解释、历史和增强页面可用，且安全边界明确。项目下一阶段的重点不应是把课程原型包装成“企业级网关”，而是让每个结论都更可复现、更容易审计：说明指标来自哪里、规则为什么命中、反馈如何沉淀、黑名单如何更新，以及异常输入为何被拒绝。

在完成 P0 项后，可再冻结一次共享契约和演示脚本；只有当指标口径、反馈记录和安全回归测试稳定后，才建议继续扩展结构化模型特征和批量能力。
